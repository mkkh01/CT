# Incident analysis — 2026-08-12

The service started correctly with four user-selected Spot pairs: LINKUSDT, NEARUSDT, XLMUSDT, and XRPUSDT, with 30 USDT assigned to each. Binance WebSocket connected and later `summary_cycle` reported `websocket_connected: true` and live prices for all four pairs.

The first set of warnings came from the REST bootstrap for 1h and 4h klines. Binance returned HTTP 418 for every requested pair and interval. The same WebSocket session continued to deliver miniTicker prices, but no closed 4h candles were available and the strategy reported `NO_SIGNAL` with `closed_candles_4h: 0`. This means the current strategy was not ready to make a reliable 4h-filtered decision even though live prices were present.

A Supabase REST read for recent signals failed with `SSL: DECRYPTION_FAILED_OR_BAD_RECORD_MAC`. This is a transient TLS/connection failure, not evidence that the query itself is malformed. The dashboard should show the failure as a warning while allowing in-memory monitoring to continue, and storage reads should use bounded retries with backoff and a session refresh.

Telegram reported HTTP 409 polling conflicts twice. That means another polling consumer or an old process still uses the same bot token. This must be resolved operationally by keeping one polling consumer only; code cannot safely make two consumers share the same token.

The dashboard should show a clear system readiness state: live prices may be available while strategy bootstrap is incomplete. It should display per-symbol 1h/4h candle counts, bootstrap status, last decision, signal/rejection reason, and a summary cycle with warnings and errors.


## External reference

Binance's official REST documentation states that repeated rate-limit violations or failure to back off after HTTP 429 can lead to an automated IP ban with HTTP 418. The relevant source is [Binance General REST API Information](https://developers.binance.com/en/docs/products/spot/rest-api). The implementation should therefore avoid making one REST bootstrap request per symbol/interval at every restart, honor `Retry-After` and rate-limit headers, back off after 418/429, and keep WebSocket prices available while historical bootstrap is unavailable.


Binance's official Market Data Only documentation recommends `https://data-api.binance.vision` for public market-data APIs that do not require authentication. This is the preferred REST bootstrap endpoint for klines in this service, while the WebSocket stream remains the live source: [Binance Market Data Only URLs](https://developers.binance.com/en/docs/products/spot/faqs/market_data_only).


## Bootstrap analysis from Render log

At 09:00:14 UTC, the first REST kline request received HTTP 418 and set a cooldown until 09:05:56 UTC. Because the previous implementation did not retry bootstrap in the background, all selected symbols remained at zero historical candles even though WebSocket prices became live at 09:01:15 UTC. The system therefore correctly avoided analysis, but the `history_incomplete` state persisted.

The revised implementation now uses Binance's public WebSocket API `wss://ws-api.binance.com:443/ws-api/v3` as an immediate fallback for public `klines` requests when REST returns 418/429, retries incomplete bootstrap automatically after cooldown, skips already-ready intervals, and records `bootstrap_attempt`, `next_bootstrap_retry_at`, and `live_execution_closed_symbols`. Strategy evaluation still occurs only on a closed execution-timeframe candle after at least 55 closed candles exist on both 1h and 4h.

Official references: [Binance Spot WebSocket API](https://developers.binance.com/en/docs/products/spot/web-socket-api) and [Binance Spot WebSocket API Market Klines](https://developers.binance.com/en/docs/catalog/core-trading-spot-trading/api/ws-api/market).
