# تقرير مراجعة مستودع CT

**تاريخ المراجعة:** 14 أغسطس 2026

**نطاق المراجعة:** بنية التطبيق، واجهات FastAPI، دورة حياة الخدمة، تدفق بيانات Binance، التحليل والمؤشرات، الاختبار الخلفي، التخزين، Supabase، إعدادات النشر، الاختبارات، وفحص أمني ساكن.

## الخلاصة التنفيذية

المستودع قابل للتشغيل في صورته الحالية، والكود يترجم بنجاح، كما نجحت الاختبارات الموجودة عند تشغيلها بالطريقة الصحيحة عبر `python3 -m pytest`. لكن توجد مشكلات مهمة قبل اعتباره جاهزًا للإنتاج: **بعض مسارات API تقبل رموزًا وأطرًا زمنية غير صالحة وتعيد HTTP 200**، والاختبار الخلفي يعطي نتائج قد تكون مضللة بسبب احتساب الصفقات المنتهية ضمن المقام، والسماح بتداخل صفقات متعددة، وعدم تمثيل الخروج الجزئي عند TP1. كذلك لا توجد حماية وصول أو تحديد معدل للواجهات العامة، وتوجد ثغرة اعتماد معروفة في نسخة `pytest` التي يسمح بها ملف المتطلبات.

لم أعدّل ملفات التطبيق أو سلوك الإنتاج؛ التغيير الوحيد الذي أُنشئ أثناء المراجعة هو هذا التقرير.

## النتائج التفصيلية

### F-01 — مسارات التحليل والإشارات لا تتحقق من الرمز والإطار الزمني

**الشدة: عالية.** مسار `GET /api/v1/analysis/{symbol}` لا يتحقق من الرمز قبل استدعاء الخدمة، لذلك أعاد `/api/v1/analysis/NOPE` حالة `200 OK`. كما أن مساري التحليل والإشارات ذوي الإطار الزمني يعيدان `200 OK` عند استخدام إطار غير موجود مثل `banana`، بينما مسارا الشموع والاختبار الخلفي يعيدان `400 unsupported_timeframe`. هذا يخلق عقد API غير متسقًا، ويجعل العملاء يفسرون بيانات فارغة أو تحليلًا غير ذي معنى على أنه نجاح.

**الدليل التجريبي:**

| الطلب | النتيجة الفعلية |
|---|---|
| `GET /api/v1/analysis/NOPE` | `200 OK` |
| `GET /api/v1/analysis/BTCUSDT/banana` | `200 OK` |
| `GET /api/v1/signals/NOPE/banana` | `200 OK` |
| `GET /api/v1/candles/BTCUSDT/banana` | `400 unsupported_timeframe` |

**الإصلاح المقترح:** إضافة تحقق موحد قبل كل استدعاء للخدمة: الرمز يجب أن يكون في `app_settings.symbols`، والإطار يجب أن يكون في `SUPPORTED_TIMEFRAMES`، مع إعادة `404` للرمز و`400` للإطار. يجب أيضًا تطبيق التحقق على مسار التحليل الافتراضي، لا المسار ذي الإطار فقط، وإضافة اختبارات عقود لهذه الحالات.

### F-02 — نتائج الاختبار الخلفي قابلة للتضليل

**الشدة: عالية.** في `run_backtest` يتم إنشاء إشارة عند كل شمعة ثم فحص جميع الشموع المستقبلية، من دون إدارة مركز موحد أو منع تداخل الإشارات. ونتيجة ذلك أن إشارات كثيرة يمكن أن تُحتسب كصفقات نشطة في الوقت نفسه، وهو ما لا يمثل عادةً محفظة أو حسابًا واحدًا.

كذلك تُضاف الصفقات المنتهية (`EXPIRED`) إلى `trades` وتدخل في `activated_trades` والمقام المستخدم في `win_rate` و`loss_rate`، مع `pnl_r = 0`. لذلك قد لا يساوي مجموع نسب الفوز والخسارة نسبة الصفقات المحتسبة، وقد تنخفض النتائج بسبب صفقات لم تُفعّل أصلًا. يجب فصل `signals_generated` و`pending_expired` و`activated_trades` بوضوح.

ويُعامل الوصول إلى TP1 على أنه خروج كامل بقيمة `+1R` في السطر 45، رغم أن النموذج يعرّف TP1 وTP2 معًا ولا يوضح تنفيذًا جزئيًا. إذا كان المقصود استراتيجية خروج جزئي، فالنتيجة الحالية تبالغ أو تغيّر الأداء الفعلي. كما أن الشمعة التي تلمس وقف الخسارة والهدف معًا تُحسم دائمًا إلى SL، وهو افتراض محافظ مقبول فقط إذا وُثّق بوضوح.

**الإصلاح المقترح:** تحديد نموذج تنفيذ صريح: مركز واحد لكل رمز/إطار أو عدد مراكز محدد، منع الإشارات المتداخلة، فصل الصفقات التي لم تُفعّل، تعريف نسبة الخروج عند TP1، وإضافة احتساب الرسوم والانزلاق السعري. يجب إضافة اختبارات للحالات: تداخل إشارتين، انتهاء إشارة قبل الدخول، لمس SL وTP في الشمعة نفسها، والوصول إلى TP1 ثم TP2.

### F-03 — واجهات عامة بلا مصادقة أو تحديد معدل

**الشدة: متوسطة، وقد تصبح عالية حسب طبيعة النشر.** التطبيق يفعّل CORS على جميع المصادر (`allow_origins=["*"]`) ويعرّض مسارات الشموع والتحليل والإشارات والاختبار الخلفي دون مصادقة أو rate limiting. هذا قد يكون مقصودًا لتغذية لوحة عامة، لكنه يسمح لأي طرف باستدعاء backtest مرارًا، وإجبار الخدمة على تحميل تاريخ Binance عند الحاجة، واستهلاك الاتصالات والذاكرة. كما أن `/api/v1/signals/active` يعرض الإشارات الحالية لأي عميل يصل إلى الخدمة.

**الإصلاح المقترح:** فصل واجهات اللوحة العامة عن الواجهات التشغيلية، إضافة مصادقة أو مفتاح وصول للمسارات الحساسة، تحديد معدل لكل IP، وضع مهلة وميزانية تنفيذ للاختبار الخلفي، تحديد حجم الاستجابة، وتقييد CORS إلى نطاقات الواجهة الفعلية بدل wildcard. إذا كان فتح الواجهات مقصودًا، فيجب توثيق ذلك مع إضافة حماية على مستوى Render أو reverse proxy.

### F-04 — نسخة pytest المسموح بها تحتوي على ثغرة معروفة

**الشدة: متوسطة.** `requirements.txt` يسمح بأي نسخة `pytest` من 8.x، والبيئة التي شُغّلت فيها المراجعة استخدمت `pytest 8.4.2`. أظهر `pip-audit` أن هذه النسخة تقع ضمن نطاق الثغرة `CVE-2025-71176 / GHSA-6w46-j5rx-g56g`، مع الإصلاح المقترح في `pytest 9.0.3`. الثغرة مرتبطة بإنشاء مجلدات مؤقتة على Unix، وتؤثر أساسًا على بيئات الاختبار متعددة المستخدمين أو CI المشتركة.

**الإصلاح المقترح:** تحديث قيد pytest إلى نسخة مصححة، أو فصل متطلبات التطوير عن متطلبات الإنتاج، ثم إعادة توليد ملف lock موحّد مع تشغيل `pip-audit` في CI. لا ينبغي تثبيت نطاق واسع مثل `pytest>=8,<9` دون فحص دوري للثغرات.

### F-05 — دورة حياة الإشارات لا توثق أو تطبق إدارة المخاطر الكاملة

**الشدة: متوسطة.** الخدمة تنقل الإشارة إلى `ACTIVE` عند لمس سعر الدخول، ثم تنقلها إلى `TP1_HIT` عند لمس TP1، ولا يوجد في هذا المسار تنفيذ جزئي أو حالة لاحقة تتابع الجزء المتبقي للوصول إلى TP2. وبمجرد أن تصبح الحالة `TP1_HIT` تتوقف `_update_signal_lifecycle` عن معالجتها لأنها ضمن الحالات النهائية. هذا يجعل TP2 غير قابل للوصول بعد TP1 في دورة الحياة الحية، على خلاف وجود TP2 في النموذج والاختبار الخلفي.

هذا تعارض وظيفي بين التشغيل الحي والاختبار الخلفي: الاختبار الخلفي يمكنه تسجيل TP2 مباشرة، بينما الخدمة الحية تنهي الإشارة عند TP1. يجب تحديد ما إذا كان TP1 إغلاقًا كاملًا أم جزئيًا، ثم توحيد آلة الحالات والاختبارات بين المسارين.

### F-06 — أمر `pytest` لا يعمل مباشرة في بيئة المراجعة

**الشدة: منخفضة.** تشغيل `pytest -q` من جذر المستودع فشل أثناء جمع الاختبارات بـ `ModuleNotFoundError: No module named 'app'`، بينما نجح `python3 -m pytest -q` بنتيجة 8 اختبارات ناجحة. لا توجد `pyproject.toml` أو `pytest.ini` أو `setup.cfg` أو `conftest.py` لتثبيت مسار المشروع أو تعريف إعدادات الاختبار.

قد تكون المشكلة خاصة ببيئة التشغيل أو script entrypoint، لكنها تجعل CI وأدوات المطورين أقل قابلية للتكرار. **الإصلاح المقترح:** إضافة `pyproject.toml` مع إعداد pytest، وإضافة حزمة المشروع أو تثبيت editable package، ثم توحيد أمر CI.

### F-07 — تغطية الاختبارات لا تشمل الحالات الحرجة

**الشدة: منخفضة حاليًا، لكنها ترفع مخاطر F-01 وF-02 وF-05.** الاختبارات الحالية تغطي المؤشرات الأساسية، صحة الشمعة، بعض عقود API، تطبيع Binance، وتخزين الشموع. لكنها لا تختبر التحقق من مدخلات التحليل والإشارات، ولا تداخل الصفقات، ولا انتهاء الإشارة، ولا انتقال TP1/TP2، ولا فشل Redis/Supabase، ولا انقطاع WebSocket وإعادة الاتصال، ولا امتلاء طوابير WebSocket.

**الإصلاح المقترح:** إضافة اختبارات وحدات وآلية للحالات المذكورة، وتشغيلها في CI باستخدام نسخة Python محددة، مع تقرير تغطية أدنى للطبقات الحرجة.

## ترتيب الإصلاح المقترح

ابدأ بتوحيد تحقق API وإضافة اختبارات له، لأن الخطأ سهل الإصلاح ويمنع بيانات نجاح زائفة. بعد ذلك وحّد آلة حالات الإشارة الحية مع backtest، ثم أصلح نموذج backtest ليمنع التداخل ويفصل الإشارات غير المفعلة. بالتوازي، حدّث pytest وأضف فحص `pip-audit` إلى CI. قبل النشر العام، أضف rate limiting ومصادقة أو قيود وصول مناسبة، وضيّق CORS.

## الحكم النهائي

**المستودع مناسب كنموذج MVP تجريبي، وليس جاهزًا بعد كنظام تداول أو خدمة عامة إنتاجية دون معالجة F-01 وF-02 وF-05.** الاختبارات الحالية ناجحة لكنها لا تغطي أكثر المخاطر تأثيرًا على صحة الإشارات وصدق نتائج الاختبار الخلفي. لا يوجد في المراجعة دليل على تسريب أسرار أو استخدام دوال تنفيذ خطرة داخل الكود، لكن سطح API العام واعتماد الاختبار القديم يستحقان معالجة قبل التوسع.
