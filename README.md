# CT — نظام توصيات Binance Spot الحية

هذا المستودع يحتوي على نظام **توصيات ومتابعة افتراضية فقط** لتداول Binance Spot. لا يقبل مفاتيح Binance API، ولا يربط محفظة، ولا يرسل أوامر شراء أو بيع. يقرأ بيانات السوق العامة عبر Binance Spot WebSocket، يبني إشارة بعد إغلاق شمعة 1H مع فلتر اتجاه 4H، ثم يرسل التنبيه إلى Telegram ويتابع نتيجة الصفقة افتراضياً حتى وقف الخسارة أو الهدف.

> **تنبيه مالي:** هذا النظام أداة برمجية للبحث والتنبيه، وليس مستشاراً مالياً ولا ضماناً للربح. قد تفشل التوصية أو تتأخر البيانات أو يحدث انزلاق سعري. لا تستخدمه لاتخاذ قرار مالي دون مراجعة مستقلة.

## ما ينفذه النظام

| الوظيفة | السلوك |
|---|---|
| مصدر الأسعار | Binance Spot WebSocket العام، مع bootstrap للشموع عبر REST العام عند بدء الخدمة |
| الإطار التنفيذي | 1H بعد إغلاق الشمعة، مع فلتر اتجاه 4H |
| الأزواج | يحددها المستخدم من Telegram؛ لا توجد قائمة إجبارية ثابتة |
| رأس المال | يحدده المستخدم لكل عملة من Telegram؛ يستخدم النظام كامل المبلغ المعرّف للمتابعة الافتراضية للصفقة |
| المراكز المتزامنة | 5 كحد أقصى |
| وقف الخسارة | 1.5% افتراضياً من سعر الدخول، قابل للتعديل من متغير البيئة قبل التشغيل |
| الهدف | 2R افتراضياً، أي نحو 3% عندما يكون وقف الخسارة 1.5% |
| الخسارة اليومية | 9% من إجمالي رأس المال المعرّف؛ عند بلوغها يتوقف فتح متابعات جديدة حتى بداية اليوم UTC التالي |
| التنفيذ | معطل بالكامل؛ كل صفقة افتراضية وليست أمراً حقيقياً |
| التخزين | Supabase للسجل الدائم وRedis للتخزين المؤقت والملخصات |
| السجلات | stdout عبر Python logging، وتظهر في Render Logs بصيغة `summary_cycle` وأحداث الاتصال والإشارات والإغلاق |

## أزرار Telegram

بعد تشغيل البوت وإرسال `/start` تظهر لوحة ديناميكية. زر **إدارة العملات ورأس المال** يستقبل في رسالة واحدة `أضف <SYMBOL> <AMOUNT>` أو `عدّل <SYMBOL> <AMOUNT>` أو `احذف <SYMBOL>` أو `القائمة`. وتظهر أزرار `🔎 SYMBOL` تلقائياً لكل عملة مضافة، بينما تعرض أزرار الأسعار والأداء والصفقات والحالة آخر معلومات متاحة من المحرك.

| الزر | النتيجة |
|---|---|
| إدارة العملات ورأس المال | إضافة أو تعديل أو حذف الزوج ورأس ماله في أمر واحد؛ مثل `أضف <SYMBOL> <AMOUNT>` أو `عدّل <SYMBOL> <AMOUNT>` أو `احذف <SYMBOL>` |
| أزرار العملات الديناميكية | يظهر زر `🔎 SYMBOL` لكل زوج أضافه المستخدم لعرض سعره ومتابعته وإشارته |
| الأسعار الحية | عرض آخر أسعار وصلت من WebSocket |
| أداء النظام | عرض PnL الافتراضي اليومي ونسبة استخدام حد الخسارة |
| الصفقات | عرض المراكز الافتراضية المفتوحة وسعر الدخول والوقف والهدف وPnL العائم |
| الحالة | عرض اتصال WebSocket، آخر حدث، عدد المراكز، والتكاملات الناقصة |
| Dashboard | افتح `/` أو `/dashboard` مباشرة لمشاهدة الأداء والأسعار والإشارات والصفقات والأحداث والأخطاء والتحذيرات |

عند تحقق شروط الإشارة، يرسل البوت رسالة تتضمن الزوج، سعر الدخول المرجعي، وقف الخسارة، الهدف، نسبة Risk/Reward، سبب الإشارة، وتأكيداً صريحاً بأن النظام لم يرسل أمراً إلى Binance. وعند وصول السعر إلى الوقف أو الهدف الافتراضي، يرسل رسالة انتهاء الصفقة والنتيجة الافتراضية. وتُبنى لوحة Telegram من قائمة المستخدم الحالية؛ فلا تظهر BTCUSDT أو ETHUSDT إلا إذا أضافهما المستخدم، وتُزال العملة من WebSocket والأسعار والإشارات عند حذفها.

يسجل Render كل دقيقة `summary_cycle` متضمناً قائمة العملات المضافة، رأس المال لكل عملة، الأسعار الأخيرة، اتصال WebSocket، اسم الاستراتيجية، عدد دورات الشموع، عدد الإشارات، الإشارات المرفوضة، الصفقات المفتوحة والمغلقة، آخر قرار استراتيجي، وآخر إشارة. كما يسجل `market_price_update` دورياً لكل زوج، و`strategy_cycle` بعد كل شمعة مغلقة، و`virtual_trade_closed` عند إغلاق المتابعة الافتراضية. ويُحدّث النظام جدول `runtime_state` في Supabase كصف واحد للحالة الحالية، بينما تبقى `system_events` سجلاً تاريخياً لا يُستخدم وحده للحكم على اتصال WebSocket الحالي.

## Dashboard

تتوفر لوحة مراقبة عامة على `/` و`/dashboard`، وتفتح مباشرة دون رمز أو ترويسة مصادقة. تعرض اللوحة حالة runtime وBinance WebSocket، العملات ورأس المال والأسعار، PnL وحد الخسارة، دورات الاستراتيجية، الإشارات المقبولة والمرفوضة مع الأسباب، الصفقات الافتراضية، أحداث Supabase، وسجل INFO/WARNING/ERROR المحلي، إضافة إلى عمر سجل `runtime_state` وهل تتطابق قاعدة البيانات مع الحالة الحية. استخدم هذه الخدمة على Render ضمن بيئة موثوقة فقط لأنها تعرض بيانات تشغيل النظام.

## متغيرات البيئة في Render

لا تضع الأسرار داخل GitHub. استخدم **Environment Variables** في Render، مع فصل الأسماء التي وردت متلاصقة في الطلب إلى المتغيرات التالية:

| المتغير | الاستخدام |
|---|---|
| `TELEGRAM_CHAT_ID` | معرّف المحادثة المسموح لها بإدارة النظام |
| `TELEGRAM_BOT_TOKEN` | رمز البوت |
| `SUPABASE_URL` | رابط مشروع Supabase |
| `SUPABASE_KEY` | مفتاح خادمي؛ يفضل service-role server-side ولا تعرضه للمتصفح |
| `REDIS_URL` | رابط Redis أو Render Key Value المتوافق |
| `BINANCE_REST_URL` | يفضل `https://data-api.binance.vision/api/v3` لبيانات market-data-only العامة |

يوجد ملف `.env.example` يضم باقي الإعدادات الافتراضية. لا توجد أي قيمة حساسة فيه. يستخدم النظام `MAX_CONCURRENT_POSITIONS=5` و`DAILY_LOSS_LIMIT_PCT=0.09` و`STOP_LOSS_PCT=0.015` و`EXECUTION_TIMEFRAME=1h` و`HIGHER_TIMEFRAME=4h` ما لم تغيرها قبل النشر.

## تهيئة Supabase

شغّل محتوى [`supabase/schema.sql`](supabase/schema.sql) مرة واحدة في SQL Editor داخل مشروع Supabase. يخزن المخطط إعدادات المستخدم، الإشارات، الصفقات الافتراضية، أحداث الإغلاق، وملخصات النظام. اجعل `SUPABASE_KEY` قيمة خادمية ولا تشاركها في Telegram أو في واجهة عامة.

## التشغيل المحلي

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
# املأ .env محلياً فقط، أو صدّر المتغيرات في جلسة التشغيل
python3 -m pytest -q
DISABLE_AUTO_START=0 flask --app app.main:app run --host 0.0.0.0 --port 8080
```

للنشر على Render استخدم `render.yaml` أو أنشئ Web Service من هذا المستودع، واختر Python، واترك أمر البناء `pip install -r requirements.txt` وأمر التشغيل `gunicorn --workers 1 --threads 2 --timeout 120 --bind 0.0.0.0:$PORT app.main:app`. وجود worker واحد مهم حتى لا تتكرر اتصالات WebSocket وTelegram polling.

## Render Free وWebSocket

يستخدم النظام WebSocket لأنه أنسب لتدفق الأسعار والشموع الحية من الاستطلاع المتكرر. يحتوي العميل على إعادة اتصال تلقائية، heartbeat، تحليل رسائل غير صالحة، وbootstrap عند البداية. ويستخدم bootstrap الافتراضي endpoint Binance العام `https://data-api.binance.vision/api/v3`، بينما تبقى أسعار WebSocket مستقلة عن REST. عند HTTP 418 أو 429 يتوقف bootstrap مؤقتاً مع backoff ولا يكرر الطلب لكل عملة.

تحتاج الاستراتيجية إلى 55 شمعة مغلقة على الأقل في كل من 1H و4H. لذلك تعرض Dashboard حالة `DATA_NOT_READY` عندما تصل الأسعار الحية لكن لا تكتمل بيانات الشموع، بدلاً من عرض ذلك كأنه `NO_SIGNAL`. يجب مراقبة `/healthz` وRender Logs، وعدم اعتبار عدم وجود توصيات دليلاً على عدم وجود فرص قبل التأكد من أن WebSocket متصل، وأن كل إطار بلغ عدد الشموع المطلوب.

Redis مناسب للكاش والملخص السريع، لكن Supabase هو مصدر الحقيقة الدائم. إذا كان Redis من Render Free أو خدمة مؤقتة فلا تعتمد عليه وحده لاستعادة الصفقات؛ يعيد النظام الإعدادات من Supabase عند بدء التشغيل.

## أمان Supabase

أظهر فحص مشروع `Trading_bot` أن جداول قديمة موجودة مسبقاً، منها `candles` و`decisions` و`simulated_trades` و`ws_checkpoints` و`performance_snapshots` و`coins` و`user_config_v4` و`tracked_coins_v4` و`live_trades_v4` و`shadow_trades_v4` و`decision_component_signals`، لديها RLS معطل. هذا يعني أن استخدام anon key مع PostgREST قد يعرّض البيانات للقراءة أو التعديل. لم أطبّق إصلاحاً تلقائياً على هذه الجداول لأن تفعيل RLS بلا سياسات قد يمنع الوصول الحالي؛ يجب مراجعتها وإضافة سياسات مناسبة قبل تعريض أي مفتاح للعميل.

الجداول الجديدة للنظام (`bot_settings` و`signals` و`virtual_positions` و`trade_events` و`system_events`) أنشئت مع RLS مفعّل ومن دون سياسات عامة. هذا مقصود لأن التطبيق خادمي: استخدم مفتاحاً خادمياً في `SUPABASE_KEY` على Render فقط، ولا تضعه في HTML أو JavaScript أو Telegram. إذا أردت استخدام anon key، يجب أولاً تصميم سياسات RLS مبنية على هوية المستخدم، وهو خارج نطاق هذه النسخة.

## حدود مهمة

النظام لا يضمن تنفيذ سعر الدخول أو وقف الخسارة لأن جميع الصفقات افتراضية، كما لا يضمن ألا تتجاوز الحركة السريعة أو انقطاع الشبكة الحد النظري للخسارة. لا يستخدم Futures أو الرافعة أو averaging down أو martingale. الإشارة ليست توصية مالية شخصية، وهي نتيجة قواعد آلية ثابتة يجب اختبارها وفهمها قبل الاعتماد عليها.
