# CT — نظام توصيات Binance Spot الحية

هذا المستودع يحتوي على نظام **توصيات ومتابعة افتراضية فقط** لتداول Binance Spot. لا يقبل مفاتيح Binance API، ولا يربط محفظة، ولا يرسل أوامر شراء أو بيع. يقرأ بيانات السوق العامة عبر Binance Spot WebSocket، يبني إشارة بعد إغلاق شمعة 1H مع فلتر اتجاه 4H، ثم يرسل التنبيه إلى Telegram ويتابع نتيجة الصفقة افتراضياً حتى وقف الخسارة أو الهدف.

> **تنبيه مالي:** هذا النظام أداة برمجية للبحث والتنبيه، وليس مستشاراً مالياً ولا ضماناً للربح. قد تفشل التوصية أو تتأخر البيانات أو يحدث انزلاق سعري. لا تستخدمه لاتخاذ قرار مالي دون مراجعة مستقلة.

## ما ينفذه النظام

| الوظيفة | السلوك |
|---|---|
| مصدر الأسعار | Binance Spot WebSocket العام، مع bootstrap للشموع عبر REST العام عند بدء الخدمة |
| الإطار التنفيذي | 1H بعد إغلاق الشمعة، مع فلتر اتجاه 4H |
| الأزواج | يحددها المستخدم من Telegram؛ لا توجد قائمة إجبارية ثابتة |
| رأس المال | يحدده المستخدم لكل عملة من Telegram؛ يستخدم النظام كامل المبلغ المعرّف للمتابعة الافتراضية للصفقة |
| المراكز المتزامنة | 5 كحد أقصى |
| وقف الخسارة | 1.5% افتراضياً من سعر الدخول، قابل للتعديل من متغير البيئة قبل التشغيل |
| الهدف | 2R افتراضياً، أي نحو 3% عندما يكون وقف الخسارة 1.5% |
| الخسارة اليومية | 9% من إجمالي رأس المال المعرّف؛ عند بلوغها يتوقف فتح متابعات جديدة حتى بداية اليوم UTC التالي |
| التنفيذ | معطل بالكامل؛ كل صفقة افتراضية وليست أمراً حقيقياً |
| التخزين | Supabase للسجل الدائم وRedis للتخزين المؤقت والملخصات |
| السجلات | stdout عبر Python logging، وتظهر في Render Logs بصيغة `summary_cycle` وأحداث الاتصال والإشارات والإغلاق |

## أزرار Telegram

بعد تشغيل البوت وإرسال `/start` تظهر الأزرار التالية. زر **إضافة رأس مال** يستقبل صيغة مثل `BTCUSDT 50`، وزر **إدارة العملات** يستقبل `أضف BTCUSDT` أو `احذف BTCUSDT`. وتعرض أزرار الأسعار والأداء والصفقات والحالة آخر معلومات متاحة من المحرك.

| الزر | النتيجة |
|---|---|
| إضافة رأس مال | حفظ رأس المال الافتراضي لكل زوج؛ مثال `BTCUSDT 50` |
| إدارة العملات | إضافة أو حذف زوج من المتابعة |
| الأسعار الحية | عرض آخر أسعار وصلت من WebSocket |
| أداء النظام | عرض PnL الافتراضي اليومي ونسبة استخدام حد الخسارة |
| الصفقات | عرض المراكز الافتراضية المفتوحة وسعر الدخول والوقف والهدف وPnL العائم |
| الحالة | عرض اتصال WebSocket، آخر حدث، عدد المراكز، والتكاملات الناقصة |

عند تحقق شروط الإشارة، يرسل البوت رسالة تتضمن الزوج، سعر الدخول المرجعي، وقف الخسارة، الهدف، نسبة Risk/Reward، سبب الإشارة، وتأكيداً صريحاً بأن النظام لم يرسل أمراً إلى Binance. وعند وصول السعر إلى الوقف أو الهدف الافتراضي، يرسل رسالة انتهاء الصفقة والنتيجة الافتراضية.

## متغيرات البيئة في Render

لا تضع الأسرار داخل GitHub. استخدم **Environment Variables** في Render، مع فصل الأسماء التي وردت متلاصقة في الطلب إلى المتغيرات التالية:

| المتغير | الاستخدام |
|---|---|
| `TELEGRAM_CHAT_ID` | معرّف المحادثة المسموح لها بإدارة النظام |
| `TELEGRAM_BOT_TOKEN` | رمز Telegram Bot API |
| `SUPABASE_URL` | رابط مشروع Supabase |
| `SUPABASE_KEY` | مفتاح خادمي؛ يفضل service-role server-side ولا تعرضه للمتصفح |
| `REDIS_URL` | رابط Redis أو Render Key Value المتوافق |

يوجد ملف `.env.example` يضم باقي الإعدادات الافتراضية. لا توجد أي قيمة حساسة فيه. يستخدم النظام `MAX_CONCURRENT_POSITIONS=5` و`DAILY_LOSS_LIMIT_PCT=0.09` و`STOP_LOSS_PCT=0.015` و`EXECUTION_TIMEFRAME=1h` و`HIGHER_TIMEFRAME=4h` ما لم تغيرها قبل النشر.

## تهيئة Supabase

شغّل محتوى [`supabase/schema.sql`](supabase/schema.sql) مرة واحدة في SQL Editor داخل مشروع Supabase. يخزن المخطط إعدادات المستخدم، الإشارات، الصفقات الافتراضية، أحداث الإغلاق، وملخصات النظام. اجعل `SUPABASE_KEY` قيمة خادمية ولا تشاركها في Telegram أو في واجهة عامة.

## التشغيل المحلي

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
# املأ .env محلياً فقط، أو صدّر المتغيرات في جلسة التشغيل
python3 -m pytest -q
DISABLE_AUTO_START=0 flask --app app.main:app run --host 0.0.0.0 --port 8080
```

للنشر على Render استخدم `render.yaml` أو أنشئ Web Service من هذا المستودع، واختر Python، واترك أمر البناء `pip install -r requirements.txt` وأمر التشغيل `gunicorn --workers 1 --threads 2 --timeout 120 --bind 0.0.0.0:$PORT app.main:app`. وجود worker واحد مهم حتى لا تتكرر اتصالات WebSocket وTelegram polling.

## Render Free وWebSocket

يستخدم النظام WebSocket لأنه أنسب لتدفق الأسعار والشموع الحية من الاستطلاع المتكرر. يحتوي العميل على إعادة اتصال تلقائية، heartbeat، تحليل رسائل غير صالحة، وbootstrap عند البداية. ومع ذلك، فإن Render Free قد يوقف الخدمة عند غياب traffic وارد؛ مسؤولية إبقاء الخدمة نشطة تقع على المشغّل كما طلب المستخدم. يجب مراقبة `/healthz` وRender Logs، وعدم اعتبار عدم وجود توصيات دليلاً على عدم وجود فرص قبل التأكد من أن WebSocket متصل وآخر حدث حديث.

Redis مناسب للكاش والملخص السريع، لكن Supabase هو مصدر الحقيقة الدائم. إذا كان Redis من Render Free أو خدمة مؤقتة فلا تعتمد عليه وحده لاستعادة الصفقات؛ يعيد النظام الإعدادات من Supabase عند بدء التشغيل.

## ملفات النظام

| المسار | الدور |
|---|---|
| `app/binance_ws.py` | WebSocket العام، bootstrap، heartbeat وإعادة الاتصال |
| `app/strategy.py` | فلتر 4H، شروط 1H، وإنتاج الإشارة |
| `app/virtual_trading.py` | محاكاة المراكز والوقف والهدف وحدود الخسارة |
| `app/runtime.py` | ربط البيانات بالاستراتيجية والتخزين والتنبيهات وsummary cycle |
| `app/telegram_bot.py` | polling وأزرار Telegram وإدارة المستخدم |
| `app/storage.py` | Supabase REST وRedis |
| `app/main.py` | Flask health server وAPI الحالة |
| `supabase/schema.sql` | الجداول والفهارس وسياسة RLS |
| `render.yaml` | إعداد Web Service أحادي العملية |

## حدود مهمة

النظام لا يضمن تنفيذ سعر الدخول أو وقف الخسارة لأن جميع الصفقات افتراضية، كما لا يضمن ألا تتجاوز الحركة السريعة أو انقطاع الشبكة الحد النظري للخسارة. لا يستخدم Futures أو الرافعة أو averaging down أو martingale. الإشارة ليست توصية مالية شخصية، وهي نتيجة قواعد آلية ثابتة يجب اختبارها وفهمها قبل الاعتماد عليها.
